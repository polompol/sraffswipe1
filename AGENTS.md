# StaffSwipe — AI entrypoint

Этот файл — первая точка входа для coding-agent'а. Если ты открыл репозиторий впервые, прочитай его до изменений.

## 30 секунд о продукте

StaffSwipe — Telegram Mini App для подработок в HoReCa. Две стороны:

- `seeker` — сотрудник ищет смену;
- `employer` — заведение ищет сотрудника.

Основной цикл: **профиль → лента → свайп → взаимный мэтч → чат → подтверждение смены → фактический выход → закрытие смены → комиссия сервиса → отзыв / акт**.

Клиент: `tma/` — React + TypeScript + Vite + Telegram Mini App SDK.  
Backend: `backend/` — FastAPI + SQLAlchemy + Pydantic + aiogram.  
Прод: `docker-compose.prod.yml` + Caddy + Postgres + API + bot + scheduler + SPA.

## Критические доменные инварианты — НЕ ЛОМАТЬ

Подробности в `CLAUDE.md`; ниже короткая версия.

1. **Молчание после договорённой смены = смена состоялась**, если никто явно не нажал «Смена не состоялась». Автозакрытие делает scheduler после окна ожидания.
2. Для расчёта достаточно подтверждения работника; заведение не может бесплатно избежать комиссии простым молчанием.
3. **Код прихода — доказательство, а не триггер денег.** Не делай оплату зависимой от того, назвал ли работодатель код.
4. Комиссия сервиса сейчас **10% только с закрытой смены**. Идемпотентность по `match_id` обязательна.
5. Денежные балансы меняются только атомарно. Никаких read-modify-write для списаний.
6. Идентичность пользователя = `tg_id`.
7. Не хранить фото медицинских книжек/документов — только статусы.
8. ИНН, телефон и другая чувствительная информация не должны попадать в публичную ленту.
9. В production нельзя ослаблять `assert_production_safe()` и Telegram initData validation.
10. Любая новая фича оценивается с точки зрения злоумышленника: что можно накрутить, обойти или списать дважды.

## Монетизация: что реально разрешено сейчас

Текущая продуктовая политика в `README.md` и `docs/COMMISSION.md`:

- публикация смен бесплатна;
- свайпы/отклики бесплатны;
- чат бесплатен;
- нет платного поднятия в ленте;
- нет внутренней валюты;
- нет подписки `StaffSwipe Pro`;
- доход сервиса — **10% от реально закрытой смены**.

Дизайн-концепты могут содержать будущие идеи. **Не реализуй их как факт**, пока пользователь отдельно не изменит продуктовую политику.

## Главная UX-идея

StaffSwipe должен ощущаться как быстрый рабочий marketplace, а не как hh.ru и не как dating-app.

Пользователь за 1–3 секунды должен понять:

- кто / какое заведение перед ним;
- роль;
- когда смена;
- сколько платят;
- насколько можно доверять другой стороне;
- что сделать дальше.

Свайп — главное движение: вправо позитивное действие, влево пропуск. У заведения терминология рабочая: «Позвать/Пригласить», а не романтическое «Хочу».

## Визуальный язык

Не придумывать другую палитру.

- brand crimson: `#a51c30` через токены `--gold` / `--gold-fill`;
- ivory background: `#efe7d3` через `--bg`;
- card: `#fffdf8`;
- text: `#241f1b`;
- gold semantic accent: `#c39a3a` через `--super`;
- success: `#2f7a4d`.

Display-шрифт — Prata. UI — системный font stack. Touch-target минимум 44px. Одна главная заливная CTA на экран. Учитывать dark mode, large mode и `prefers-reduced-motion`.

## Как работать с задачей

Перед изменением:

1. Определи роль: seeker, employer или обе.
2. Найди существующий компонент — не создавай дубль без причины.
3. Проверь API/type: не рисуй данные, которых backend не отдаёт.
4. Если нужен новый field — меняй backend schema/model/endpoint + TS type + mock + миграцию + тесты.
5. Сохраняй доменные инварианты выше.
6. После изменения запусти проверки.

## Проверки после правок

```bash
# backend
cd backend
ruff check . && python -m pytest -q

# frontend
cd tma
npm run lint
npx tsc --noEmit
npx vitest run
npm run build

# весь проект
bash scripts/verify.sh

# e2e при изменениях user flow/layout
bash scripts/e2e.sh
```

Не сообщай «готово», если проверки не запускались. В таком случае явно напиши: «код изменён, проверки не запускались».
