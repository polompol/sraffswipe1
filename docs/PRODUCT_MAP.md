# StaffSwipe — карта продукта

Документ объясняет продукт целиком без необходимости читать весь код. Он не заменяет код и `CLAUDE.md`: при конфликте главный источник — работающий код + тесты.

## 1. Роли

### Seeker — сотрудник

Ищет смены и подработки. Основные действия:

- заполнить профиль;
- указать роли, город, медкнижку и доступность;
- смотреть смены;
- фильтровать;
- свайпать вправо/влево;
- получить взаимный match;
- общаться в чате;
- подтвердить смену;
- при необходимости использовать код прихода как доказательство;
- завершить смену / оспорить неявку;
- получить акт для самозанятого;
- оставить отзыв.

### Employer — заведение

Ищет персонал на опубликованные смены. Основные действия:

- заполнить профиль заведения;
- пройти доступную верификацию;
- создать вакансию/смену;
- смотреть кандидатов;
- фильтровать по роли, району, доступности и надёжности;
- позвать кандидата;
- получить взаимный match;
- общаться в чате;
- подтвердить или отменить смену по правилам;
- пополнить баланс;
- оплатить комиссию после закрытой смены;
- участвовать в споре, если смена не состоялась;
- оставить отзыв.

## 2. Основной end-to-end путь

```text
Telegram
  ↓
Авторизация по initData / tg_id
  ↓
Выбор роли + профиль
  ↓
Лента
  ↓
Swipe
  ├─ dislike → следующая карточка
  └─ like → сервер проверяет взаимность
                 ↓
               Match
                 ↓
                Chat
                 ↓
       Подтверждение смены
                 ↓
      Смена должна состояться
          ↓               ↓
      состоялась       не состоялась
          ↓               ↓
    auto/manual close     dispute / no-show
          ↓
     комиссия 10%
          ↓
      отзыв / акт
```

## 3. 12 ключевых экранов продукта

### 01 — Выбор роли / старт

Цель: за секунды объяснить две стороны marketplace.

Показывать:
- StaffSwipe;
- «Ищу смену»;
- «Ищу сотрудника»;
- вход / регистрацию.

### 02 — Регистрация / профиль

Цель: собрать минимум данных, необходимый для matching и доверия.

Seeker:
- имя;
- город;
- роли;
- доступность;
- медкнижка — только статус;
- фото профиля.

Employer:
- название;
- город / адрес;
- тип заведения;
- идентификационные данные только там, где это необходимо и безопасно;
- фото интерьера.

### 03 — Swipe смен для seeker

Главный продуктовый экран сотрудника.

За 1–3 секунды должны читаться:
- фото;
- заведение;
- роль;
- сумма за смену;
- дата/время;
- дистанция, если доступна;
- срочность;
- доверие: verified/rating/completed shifts, если backend это отдал.

Действия:
- влево — пропустить;
- вправо — откликнуться;
- сохранить в избранное;
- открыть детали.

### 04 — Swipe кандидатов для employer

Главный экран заведения.

За 1–3 секунды должны читаться:
- фото человека;
- имя + возраст, если есть;
- основная роль;
- рейтинг;
- надёжность / число смен, если есть;
- доступность сегодня;
- район;
- медкнижка.

Действия:
- влево — не подходит;
- вправо — позвать;
- открыть подробности.

### 05 — Фильтры

Seeker отвечает на вопросы:
- где;
- когда;
- кем;
- за сколько;
- насколько далеко;
- только проверенные / другие устойчивые условия, если поддержаны backend.

Employer:
- город;
- роль;
- район;
- доступность сегодня;
- надёжность.

Не добавлять в UI фильтр, если такого поля или серверной логики нет.

### 06 — Детали смены / человека

Показывает информацию, которая слишком тяжёлая для лицевой swipe-карточки.

Смена:
- полный адрес;
- подробности оплаты;
- требования;
- описание;
- дополнительные условия.

Кандидат:
- описание о себе;
- дополнительные роли;
- опыт / теги;
- документы только в виде безопасных статусов.

### 07 — Match

Состояние взаимного интереса.

Важно: терминология рабочая, а не dating-heavy.

Seeker: «Взаимно» / «Отклик принят».  
Employer: «Взаимно» / «Кандидат согласен».

Следующее действие — открыть чат / договориться о смене.

### 08 — Подтверждённая / защищённая смена

Показывает:
- кто с кем;
- конкретную вакансию;
- дату/время;
- статус подтверждения;
- код прихода, когда он доступен;
- что делать при проблеме.

Код — доказательство фактического выхода, а не условие списания денег.

### 09 — Чаты

Чаты возникают вокруг реального match/смены. Основная задача — довести взаимный интерес до конкретной договорённости.

Важно показывать контекст смены, а не превращать чат в общий мессенджер.

### 10 — Мои смены

Минимальные состояния:
- согласование;
- подтверждена;
- наступила / идёт;
- завершена;
- не состоялась;
- спор;
- истекла без подтверждения, где применимо.

Конкретные enum/status всегда брать из backend, а не из этого документа.

### 11 — Закрытие смены / деньги / отзыв

После фактической смены пользователь должен понимать:
- статус;
- итоговую сумму;
- комиссию сервиса на стороне заведения;
- возможность сообщить, что смена не состоялась;
- возможность оставить отзыв;
- возможность получить акт для самозанятого.

### 12 — Профиль

Seeker:
- фото;
- роли;
- рейтинг;
- история / надёжность;
- доступность;
- безопасные статусы документов;
- настройки темы и крупного режима.

Employer:
- данные заведения;
- рейтинг;
- опубликованные смены;
- баланс / расчёты там, где это предусмотрено продуктом;
- настройки и безопасность.

## 4. Swipe — главное действие продукта

Текущая механика уже реализована в `tma/src/features/feed/SwipeDeck.tsx` и содержит важные защитные детали:

- видимый stack из нескольких карточек;
- drag gesture;
- right = like, left = dislike;
- карточка возвращается, если сервер отказал;
- haptic;
- доступность для клавиатуры;
- flip/details;
- корректная работа при смене набора карточек;
- reduced motion.

Визуальный редизайн не должен выбрасывать эту механику и писать её заново без необходимости.

## 5. Matching

Match создаётся только при серверно подтверждённой взаимности. Клиент не должен сам «дорисовывать» match.

Для employer позитивный swipe должен относиться к реальной опубликованной смене. Если у заведения нет вакансии, UI направляет сначала создать смену.

## 6. Shift lifecycle и деньги

Ключевое правило продукта: после согласованной смены молчание не позволяет стороне бесплатно уклониться от результата.

- Явная отмена — по существующим правилам и срокам.
- После смены «не состоялась» — явное действие.
- Иначе scheduler закрывает смену по правилам проекта.
- Комиссия начисляется идемпотентно на закрытую смену.
- Если баланса недостаточно — используется существующая pending/счёт логика.

Подробности: `CLAUDE.md`, `docs/COMMISSION.md` и backend tests.

## 7. Trust & Safety

Существующие принципы:

- Telegram identity;
- проверка initData в production;
- verified employer, если проверка пройдена;
- отзывы / рейтинг;
- надёжность и история выходов;
- код прихода как доказательство;
- жалобы / reports;
- споры;
- запрет отдавать публично чувствительные данные;
- без хранения фотографий документов;
- анти-double-spend / idempotency для денег;
- rate limits.

Будущие идеи (escrow, selfie check-in) не считать реализованными до отдельного изменения продукта.

## 8. Монетизация

Текущая модель:

**10% комиссии с закрытой смены, платит заведение.**

Не часть текущего продукта:
- Pro-подписка;
- boost;
- платные места в выдаче;
- внутренняя валюта;
- платный чат.

Если продуктовая стратегия изменится — сначала изменить спецификацию/бизнес-правила, затем код.

## 9. Дизайн

Источник истины: `DESIGN_SYSTEM.md` + `tma/src/theme/theme.css`.

Характер:
- crimson + ivory;
- Prata на display-акцентах;
- крупное фото на swipe-card;
- высокая визуальная плотность полезной информации;
- одна primary CTA;
- тёплый рабочий, а не романтический язык;
- минимум 44px touch area;
- dark theme и large mode обязательны.

## 10. Что AI не должен выдумывать

Без проверки backend/types нельзя добавлять как факт:

- «ответ за 5 минут»;
- live online status;
- точное ETA до выхода;
- escrow;
- selfie verification;
- гарантированную выплату платформой;
- StaffSwipe Pro;
- новые документы;
- новые рейтинговые показатели;
- геолокационный check-in.

Если такая метрика нужна дизайну, пометь её как **future field** и перечисли изменения backend + frontend + migration + tests, которые нужны для реальной реализации.
