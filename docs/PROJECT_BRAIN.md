## Что такое StaffSwipe

Telegram Mini App для HoReCa: двусторонний marketplace сотрудников и заведений в логике swipe → взаимный интерес → match → подтверждение смены → фактический выход → завершение/спор → репутация и комиссия.

Основные роли:
- сотрудник / соискатель;
- заведение / работодатель.

Продукт должен ощущаться очень простым, быстрым и визуально лёгким, как swipe-приложение, но оставаться серьёзным рабочим инструментом для выхода на смены.

## Техническая база

- `tma/`: React 18 + TypeScript + Vite + `@telegram-apps/sdk-react` v3, TanStack Query, Zustand, HashRouter.
- `backend/`: FastAPI + SQLAlchemy 2 + Pydantic v2 + Alembic.
- PostgreSQL в production, SQLite для dev/tests.
- `backend/bot/`: aiogram bot как отдельный процесс.
- Production: `docker-compose.prod.yml` + Caddy HTTPS + PostgreSQL + API + bot + SPA.
- E2E: Playwright в `e2e/`.

## Критичные доменные инварианты — не ломать

Подробное обоснование хранится в `CLAUDE.md` и профильных документах.

- Молчание после смены не должно позволять заведению избежать комиссии.
- Для расчёта достаточно подтверждения сотрудника в предусмотренных текущей логикой случаях.
- Код прихода — доказательство выхода, а не самостоятельный финансовый триггер.
- Комиссия — 10% и начисляется только за закрытую смену, идемпотентно по `match_id`.
- Баланс и финансовые списания меняются только атомарными операциями с условием; никаких read-modify-write для денег.
- Идентичность пользователя основана на Telegram `tg_id`; relink не должен допускать эскалацию до администратора.
- Планировщик является частью бизнес-логики: без settlement-задач смены не закрываются и комиссия не начисляется.

## UX и дизайн

- Mobile-first и Telegram Mini App-first.
- Учитывать safe-area, viewport, Telegram theme, BackButton/MainButton, haptics и появление клавиатуры.
- Минимализм важнее декоративной сложности.
- Сохранять текущую дизайн-систему: багровый `--gold:#a51c30`, слоновая кость `--bg:#efe7d3`; новые цвета только через токены в `tma/src/theme/theme.css`.
- Каждый экран/действие проектировать не только для happy path: loading, empty, error, disabled, success, retry, destructive confirmation.
- Не создавать случайный новый визуальный язык для каждого экрана.
- Тексты UI — простые, тёплые, по-русски.

## Безопасность и privacy

- Административные права проверяются на сервере, а не в клиенте.
- Секреты только через environment variables; production safety guards не ослаблять.
- Не хранить фото документов/медкнижек; хранить только необходимые статусы.
- ИНН, телефон и другие чувствительные данные не отдавать в публичных лентах/эндпоинтах.
- Каждую новую функцию до завершения проверить с позиции злоумышленника: что можно накрутить, обойти, повторить, подобрать или использовать для эскалации прав.
- Финансовые webhook/операции должны быть идемпотентными и проверять сумму/метаданные.

## Текущее состояние

По актуальной памяти репозитория продукт **готов к пилоту**; работа слита в `main`. Для реального запуска остаются внешние production-реквизиты/инфраструктура (сервер, домен, токен бота и связанные настройки — см. `docs/LAUNCH.md`).

При этом продуктовая работа продолжается: приоритет — довести UX и визуальную систему до полноценного, очень удобного Telegram Mini App без разрушения уже готовой доменной и финансовой логики.

Основные направления следующего слоя:
1. Полный UX обеих ролей: onboarding → регистрация → профиль → лента/swipe → смена → match → подтверждение → завершение/спор → рейтинг → уведомления → настройки/поддержка.
2. Единая система компонентов, кнопок, анимаций и состояний.
3. Адаптация под разные мобильные размеры и Telegram WebView.
4. Trust & Safety: жалобы, no-show, фейковые заведения, мультиаккаунты, блокировки, аудит.
5. Админка с серверной авторизацией, аудитом и минимальными привилегиями.
6. Наблюдаемость, аналитика продуктовой воронки и проверяемый production flow.
