# Operations, Recovery & Release Gate Design

## Goal

Make StaffSwipe operational failures visible and recovery verifiable without replacing the observability stack that already works.

Stage 7 focuses on three guarantees:

1. the owner can detect when a critical background capability has stopped even while the API still answers;
2. database backups are not merely created but can be restored and validated;
3. repository release status is derived from one commit SHA and cannot be confused with external production gates.

This stage must not change marketplace behavior, payment semantics, authorization, matching, moderation policy, or Telegram UI behavior.

## Existing Architecture To Preserve

- Sentry remains the error/exception aggregation layer for API, TMA and scheduler.
- Existing request timing and `X-Request-ID` logging remains the request tracing baseline.
- `/health` remains liveness only.
- `/health/ready` remains API + PostgreSQL readiness and continues to be the Docker API healthcheck.
- Redis remains an optional runtime dependency with local fallback in non-production/degraded operation.
- The existing scheduler remains a separate process using `app.scheduler` and the existing `job_runs` table for once-per-day idempotency.
- `scripts/backup.sh` remains the production backup creator and keeps the current gzip-compressed SQL format.
- Existing Backend, TMA, E2E and Security workflows remain independent source checks.

No Prometheus/Grafana/Alertmanager stack is introduced in this stage.

## Scope

### 1. Scheduler heartbeat

The scheduler must publish a durable heartbeat that is independent of `job_runs`.

`job_runs` means "this named daily task completed on this business day" and must stay dedicated to that purpose. It must not be overloaded with minute-level process liveness.

Add a small `service_heartbeats` table keyed by service name. At minimum it contains:

- `service` — unique/primary identifier such as `scheduler`;
- `updated_at` — latest UTC heartbeat timestamp.

The scheduler writes/updates its heartbeat on every main-loop iteration, before sleeping. A failed heartbeat write is logged and captured by Sentry when available, but it must not kill the scheduler loop.

The heartbeat write must be idempotent and safe if an operator accidentally starts more than one scheduler process.

### 2. Operational health endpoint

Add a separate operational endpoint, `/health/ops`.

It is intentionally separate from `/health/ready`:

- `/health/ready` answers whether the API process and database can serve requests;
- `/health/ops` answers whether the wider StaffSwipe runtime is operationally healthy.

The endpoint reports only bounded non-sensitive component status. It must never return connection strings, credentials, exception text, hostnames, stack traces, Telegram IDs, payment identifiers, or raw database errors.

Required components:

- PostgreSQL: cheap `SELECT 1` check;
- Redis: if configured, a fresh short-timeout `PING` rather than a cached success flag;
- scheduler: latest `service_heartbeats.scheduler` timestamp and whether it is fresh.

Default scheduler stale threshold: 180 seconds. The threshold may be made configurable if that is needed for clean testing/deployment, but no complex monitoring configuration framework is added.

HTTP semantics:

- 200 when all configured critical operational checks are healthy;
- 503 when PostgreSQL is unavailable, configured Redis is unavailable, the scheduler heartbeat is missing, or the scheduler heartbeat is stale;
- local/dev environments with no Redis configured may report Redis as `disabled` without failing overall health.

The production Docker API healthcheck must remain on `/health/ready`, not `/health/ops`, so a scheduler or Redis degradation alerts the operator instead of causing the API container to restart unnecessarily.

### 3. Redis operational probe

The current Redis client intentionally degrades to process-local behavior when Redis is unavailable. That fallback is preserved.

Operational health needs a separate fresh probe because the existing client caches connection initialization state. Add a minimal health probe in the Redis abstraction that:

- returns `disabled` when no `REDIS_URL` is configured;
- performs a fresh short-timeout ping when configured;
- returns healthy/unhealthy without leaking the exception outside;
- does not mutate application rate-limit/chat fallback semantics.

### 4. Backup restore verification

Production backup format remains generated by `scripts/backup.sh`:

- `pg_dump` SQL;
- `--clean --if-exists`;
- gzip compression;
- gzip integrity check;
- sanity check for a core table;
- retention/off-server copy behavior unchanged.

Add a repeatable restore verification path that proves a StaffSwipe SQL gzip backup can be restored into a disposable PostgreSQL database and queried afterwards.

The verification must:

1. operate only on a disposable/test database;
2. create known sentinel data before the dump or use a dedicated test fixture database;
3. produce a backup using the same SQL/gzip semantics as production;
4. restore into a newly created empty database;
5. assert that core schema exists;
6. assert that sentinel data survived;
7. fail loudly on a truncated/corrupt archive or failed restore;
8. destroy the disposable restore database afterwards where practical.

No production data or production credentials are used in CI.

A dedicated script may be added, for example `scripts/verify-backup-restore.sh`, and invoked by Backend CI against the existing PostgreSQL service.

### 5. Repository release gate

Add a single repository-level release-gate workflow/check whose purpose is aggregation, not duplicate testing.

It must evaluate the canonical automated checks for one exact SHA:

- TMA CI;
- Backend CI including PostgreSQL and backup/restore verification;
- E2E;
- Security.

The release gate must not claim completion based on workflow runs from different commit SHAs.

Preferred implementation: use GitHub Actions' native workflow completion/dependency mechanisms where possible. If cross-workflow aggregation requires querying GitHub's API, use only the current repository and current commit SHA, least-privilege read permissions, bounded retries, and explicit check-name matching.

The gate must be fail-closed for repository automation: missing, failed, cancelled, or timed-out required checks are not green.

### 6. External release gates remain external

Repository automation cannot prove:

- real Telegram Mini App behavior on physical iOS and Android devices;
- YooKassa test-environment payment/webhook/refund/reconciliation behavior;
- final production domain/HTTPS configuration;
- off-server backup destination actually receiving and retaining backups in the owner's production account.

These must remain explicitly documented as `PENDING` until separately verified. The repository release gate may surface this distinction in documentation or job summary, but it must never mark those external gates as automatically passed.

## Error handling

- Scheduler heartbeat failure logs the error and continues the scheduler loop.
- `/health/ops` returns sanitized component states and 503 rather than propagating raw dependency exceptions.
- Redis probe failure does not disable the application's existing fallback behavior.
- Restore verification fails on any failed shell command (`set -euo pipefail`) and cleans up temporary resources where possible.
- Release-gate automation fails closed when required evidence is absent.

## Security and privacy

- No secrets are returned from health endpoints.
- No production database is restored in CI.
- No production backup is uploaded to GitHub Actions artifacts.
- No payment or personal data is added to operational responses.
- GitHub workflow permissions stay read-only unless a concrete action needs more.
- Existing secret scanning and CodeQL coverage remains mandatory.

## Testing strategy

Implementation follows TDD.

1. Add RED backend tests for heartbeat persistence/freshness and sanitized `/health/ops` behavior.
2. Verify RED failures are due to missing Stage 7 behavior.
3. Add the minimal model/migration/scheduler/health implementation.
4. Add RED tests or executable contract checks for backup/restore verification before wiring it into CI.
5. Add the minimal restore script and Backend CI job/step.
6. Add the repository release-gate workflow without duplicating the four existing suites.
7. Run all automated gates on one final SHA.
8. Keep PR #62 Draft and unmerged.

## Non-goals

Stage 7 does not:

- replace Sentry;
- add Prometheus, Grafana, Loki, ELK, Datadog or another monitoring platform;
- make external YooKassa/Telegram checks fake CI passes;
- change Redis fallback semantics;
- make scheduler health a reason to restart the API container;
- change the production backup file format;
- restore production data in CI;
- redesign the application UI;
- change product/business rules.

## Acceptance criteria

Repository Stage 7 is complete only when:

- scheduler heartbeat is persisted and has automated coverage;
- duplicate/parallel heartbeat writes are safe;
- `/health`, `/health/ready` retain their existing contracts;
- `/health/ops` reports PostgreSQL, Redis and scheduler state without sensitive details;
- stale or missing scheduler heartbeat is detected;
- configured Redis failure is detected operationally without removing runtime fallback;
- a disposable PostgreSQL dump → gzip → restore → sentinel verification runs successfully in CI;
- corrupt/invalid backup verification fails;
- Backend CI includes the recovery verification;
- one repository release-gate check aggregates the canonical automated checks for the same SHA;
- TMA CI is green;
- Backend CI including PostgreSQL/recovery is green;
- E2E is green;
- Security is green;
- all repository checks are green on the same final SHA;
- PR #62 remains Draft and unmerged;
- physical Telegram smoke and YooKassa test-environment smoke remain explicitly external/PENDING unless separately verified.
