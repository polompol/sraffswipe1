# StaffSwipe — что готово и что осталось подключить

Проверка 10 сентября 2026. База изменений: `c58584932c23002a96f56780cd00f676064f283d`, ветка `codex/staffswipe-hospitality-design`.

## Результат

Обновлён существующий React/FastAPI проект: старт, лента двух ролей, детали, галерея, профиль, заголовки рабочих страниц, создание смены в три шага, текущие смены/история, помощь и отзыв. Сохранены реальные API, чат, приглашения, комиссия, документы и админка.

Выполненные исправления:

- У кнопок сохраняются базовые стили при передаче дополнительного класса. Нажатия внутри свайп-карточки доходят до галереи, сохранения и подробностей.
- Лента адаптирована под низкие экраны; условия не перекрываются кнопкой отклика. Нижние отступы учитывают безопасную область Telegram и устройства.
- До пяти собственных фотографий сотрудника проходят серверную проверку источника. Можно удалить фото и выбрать главное. Загрузка не допускает сохранения незавершённого файла.
- Запоздавшие ответы предыдущего аккаунта не меняют новую сессию. Одновременные ошибки авторизации используют один повторный вход. Временная потеря связи не выдаётся за выход из аккаунта.
- Повторное нажатие при регистрации блокируется; вход на реальный сервер требует Telegram. Демо явно обозначено и использует вымышленные данные.
- Некорректная подпись Telegram безопасно отклоняется. WebSocket не принимает токен доступа к документам и прекращает использование просроченного токена.
- Сбой создания платежа возвращает ошибку сервиса. Приложение не показывает вымышленную платёжную ссылку.
- Исправлено отображение календарных дат и текстов расчёта. Отзыв отправляется отдельной кнопкой после выбора оценки.

Сквозные тесты работают с настоящим FastAPI и изолированной SQLite-базой. Вход там технический, только для теста. Это не проверка реального аккаунта Telegram, банковского платежа, боевого Postgres или боевого S3.

Один backend-тест с настоящим Redis Pub/Sub пропущен: в среде проверки нет `redis-server`. Проверки с заменителями Redis выполнены. В backend-прогоне есть предупреждения зависимостей; они не приравниваются к ошибкам тестов.

Финальный сквозной прогон выполнялся отдельно от других сборок. Ранее совместный запуск двух сборок перезаписал `tma/dist` во время E2E; тот результат не используется как итоговая проверка.

## Перед запуском на реальных пользователях

| Подключение | Конкретный результат |
| --- | --- |
| Домен и приложение | Разместить проверенную ветку на выбранном HTTPS-адресе; собрать frontend с `VITE_USE_BACKEND=true` и правильным API URL. |
| Telegram | Указать адрес Mini App в настройках своего бота, проверить получение и серверную валидацию `initData`, возврат, клавиатуру, safe area на реальных iOS/Android. |
| Backend | Поднять Postgres, применить миграции; проверить API и сохранение данных после перезапуска. |
| Redis и планировщик | Проверить обмен сообщениями между процессами, ограничения запросов, напоминания и автоматическое закрытие смен. |
| Фотографии | Подключить собственное S3-совместимое хранилище; пройти загрузку → просмотр → изменение главного фото настоящим профилем. |
| Проверка компании | Настроить DaData, проверить успешный и ошибочный ИНН. Самозанятость и медкнижка не становятся проверенными от одного заполнения поля. |
| Оплата комиссии | Настроить ЮKassa, проверить создание платежа, возврат, подтверждённый webhook, повторную доставку и обновление баланса. |
| Поддержка | Указать реальный `VITE_SUPPORT_URL` и операторов админки; отправить тестовую жалобу на тестовую смену и проверить разбор. |
| Документы сервиса | Заполнить оставшиеся реквизиты/контакты оператора в существующих `docs/legal/`; проверить опубликованные страницы. |

Telegram отдельно описывает поддержку темы, безопасных областей, кнопки возврата и проверку переданных данных в [официальной документации Mini Apps](https://core.telegram.org/bots/webapps). Проверка браузерных размеров не заменяет этот последний прогон в приложениях Telegram.

Никаких новых платных подписок для этой доработки не оформлено. Higgsfield запросил тариф Basic или выше; для собственных демонстрационных изображений использован доступный инструмент генерации. Рабочее размещение и услуги провайдеров зависят от выбранной инфраструктуры: их стоимость и доступность этим прогоном не проверялись.

## Правила, которые нельзя подменять дизайном

Оплату за работу сотрудник получает непосредственно от заведения. Комиссия StaffSwipe 10% начисляется заведению; она не вычитается из показанной сотруднику ставки. Баланс в профиле заведения предназначен для комиссии. Резервирование полной оплаты труда из экрана 43 исходного примера не реализовано.

Код прихода знает заведение, сотрудник получает его на месте и вводит в приложении. Это доказательство присутствия, а не гарантия оплаты и не автоматический таймер фактических часов.

После окончания смена может закрыться, если обе стороны подтвердили выход. Планировщик также закрывает подходящие смены через 12 часов после окончания по текущим правилам сервера; спорные и явно несостоявшиеся смены требуют другой обработки. Подтверждение сотрудника в существующей модели влияет на автоматический расчёт даже при незавершённом подтверждении заведения. Дизайн не меняет эти правила. Полное двухстороннее принятие табеля из примера потребует отдельного изменения модели и тестов.

Все 50 экранов сопоставлены с реальными возможностями в [карте UX](STAFFSWIPE-UX-50.md). Серверные черновики, полный журнал исходящих приглашений, кабинет обращений, личные блокировки и новый табель отмечены там как оставшаяся работа, а не как готовые функции.

## Воспроизведение

После установки зависимостей выполнить `bash scripts/verify.sh`. Сквозные тесты запускать отдельно из `e2e` командой `npm test` с Python backend-окружения в `PATH`; не запускать одновременно другую сборку `tma/dist`.

Для просмотра без серверных ключей: `npm --prefix tma ci`, затем `npm run dev` из корня. Это демонстрационный режим. Для рабочего размещения использовать существующие инструкции `docs/DEPLOY.md` и фактические настройки окружения; старые оценки стоимости/времени в этих инструкциях не перепроверялись.
